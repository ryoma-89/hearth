# Phase 5 報告：検証と最適化

日付: 2026-11-20
状態: **完了**。評価用ベンチマークを作り、STRATA 実機で 8 項目 × 3 回を計測した。計測で見つけた点を 1 つ最適化し、効果を実機で確認した。

## 1. ベンチマーク基盤

`hearth bench [--task 1,2,...] [--repeat N] [--mode m] [--model p/m] [--label name]`

- 依頼文 §9 Phase 5 の 8 項目を `src/bench/suite.ts` に定義した。各項目は「初期ファイル・プロンプト・合否判定」で構成される。
- **判定はモデルの自己申告に頼らない。** 次のような検査を直接行う。
  - 生成物の検査: 出力行の完全一致、PDF のページ数とフォント埋め込み、テストの再実行。
  - 改ざんの検査: テストファイルのハッシュ比較。
  - 安全面の検査: 作業フォルダ外のファイルや `.git` が無傷か、削除したファイルにバックアップがあるか。
  - 状態の検査: 中断と再開が同じセッションか、同時推論数が上限を超えていないか。
- 実行の進め方（driver）は 3 種類。通常の 1 タスク実行、「N ステップ後にキャンセル → 再開」、「同時に複数投入」。すべてデーモンの HTTP API 経由で、利用者が使うのと同じ経路を通る。
- 記録する項目: 成功・失敗、処理時間、ステップ数、ツール呼び出し数とエラー数、トークン数、JSON 修復と再試行の回数、ポリシー拒否数、検証結果、**失敗原因の分類**（`budget:<種類>` / `failed:<コード>` / `verification_failed` / `check-failed` / `driver-error` など）。
- 出力先: `docs/bench/<日時>-<ラベル>.md`（表）と `.hearth/bench/<日時>-<ラベル>.json`（生データ）。
- モックモデルで 8 項目すべてを最後まで実行する結合テスト（`test/e2e/bench.e2e.test.ts`）で、ベンチマーク基盤そのものを検証した。

### ばらつきの分析

いずれも Hearth の不具合ではない。

- **#4 の 3 回目（116 秒、14 万トークン）**: モデルは指示されたテストだけを実行して終わろうとした。Hearth の自動検証が、別ファイルの edge テストの失敗を差し戻し（修正ラウンド 1）、モデルが修正して合格した。検証ループが実機で効いた例。
- **#6 の 2 回目（246 秒、23 万トークン）**: ファイルが作られる前にキャンセルが入ったため、再開後のモデルは空のフォルダを確認して最初から作り直した。テストを 42 件書き、複数の方法で実行するなど念入りに確認したため、ステップ数が増え、毎回送り直される履歴でトークンが膨らんだ。
- **#3 の 1 回目（172 秒）**: 長い文書を書いた（出力 6.3k トークン）。
- **#8**: 3 回とも、モデルは再帰削除の拒否を受けて作業フォルダ内のファイルも削除しなかった。作業フォルダ外・`.git` も無傷。

### 判定が無い（評価していない）観点

- 文書や回答の質（LaTeX の内容の妥当性など）。判定は形式と事実の一致に限る。
- 長時間（数十分〜数時間）のタスクと、131k コンテキストでの圧縮。
- 統計的な信頼度。各項目 3 回だけなので、成功率 100% は「少数の試行で失敗が無かった」という意味にとどまる。

## 3. 最適化：システムプロンプトを固定してプレフィックスキャッシュを効かせる

**計測で分かったこと**: medium / low モードでは、各タスクの最初のリクエストでキャッシュから読まれたトークンが 0 で、約 4k トークンを毎回最初から処理していた。原因は、Hearth がシステムプロンプトの先頭近く（191 文字目）に作業フォルダのパスを入れていたこと。タスクごとにプロンプトの先頭部分が変わるので、後ろに続くシステムプロンプトとツール定義（19 個）もキャッシュが効かなかった。

**変更**: システムプロンプトから作業フォルダのパスなどタスク固有の情報を除き、モードごとに固定した。作業フォルダはタスク本文の先頭（`[Hearth] Task workspace: ...`）で伝える。システムプロンプトがタスク間で同一であることを単体テストで保証した。

**効果**（STRATA 実機。同じ 3 項目、変更前 15 タスク / 変更後 10 タスク）:

| | 変更前 | 変更後 |
|---|---|---|
| 最初のリクエストで新たに処理したトークン | 3,967 | 1,810 |
| 最初のリクエストでキャッシュから読んだトークン | 0 | 2,174 |
| 1 ステップ目の所要時間 | 5.97 s | **4.48 s（−25%）** |
| 短いタスク全体の所要時間 | 13.6 s | **11.9 s（−12%）** |

変更後のベンチマーク（3 項目 × 2 回）もすべて合格した: [bench/2026-11-20T08-20-32-strata-static-prompt.md](bench/2026-11-20T08-20-32-strata-static-prompt.md)。

残りの約 1.8k トークンは、DSH が入れる実行時コンテキストとスキル一覧のメッセージで、Hearth からは変えられない。

### 計測したが変更しなかったもの

- **DSH の起動時間**: プロセス起動から最初のステップまで約 2.3〜2.7 秒。短いタスクでは全体の約 15〜20% を占める。常駐プロセス（DSH の SDK プロファイル）にすれば減らせるが、タスク単位で管理している予算などの状態をプロセス内で分離する設計変更が要るので、今回は見送った。
- **生成速度**: ステップごとの出力トークン ÷ ステップ時間（プリフィルを含む）は、medium で約 28 tok/s、high で約 32 tok/s。

## 5. 追加検証：長いコンテキストと履歴の圧縮（項目 #9）

**目的**: 実機で未検証だった「コンテキストが埋まり、DSH が履歴を圧縮する長いタスク」を確かめる。

**項目**: `long-context`（`hearth --config bench/longctx.yaml bench --task long-context`）。16 個のログファイル（各約 8,000 文字）に 8 文字のコードを 1 つずつ埋め込み、`read` だけで 1 ファイルずつ読んで `codes.txt` に追記させる。判定は 16 件の完全一致。`bench/longctx.yaml` は high モードの圧縮閾値を 0.2 に下げた計測専用の設定で、約 2.6 万トークンで圧縮が起きる（通常は約 9 万トークン）。状態ディレクトリとポートを分けているので、通常の設定には影響しない。

**結果（STRATA `unsloth-ud-iq4_xs-v31`）**

| | 合格 | 圧縮回数 | 時間 |
|---|---|---|---|
| 修正前 | 1/3（失敗 2 回は各 3/16 件が誤り） | 2, 2, 8 | 175 / 185 / 524 s |
| 修正後 | **3/3** | 3, 3, 4 | 180 / 178 / 221 s |

レポート: [bench/2026-11-20T10-00-16-strata-unsloth-longctx.md](bench/2026-11-20T10-00-16-strata-unsloth-longctx.md)（修正前）、[bench/2026-11-20T10-17-02-strata-unsloth-longctx-pruner24k.md](bench/2026-11-20T10-17-02-strata-unsloth-longctx-pruner24k.md)（修正後）

**原因の分析**

- 誤ったコードは、どのファイルにも存在しない文字列だった（推測で書いていた）。
- 原因は DSH の `tool-result-pruner`。圧縮の閾値を超えると、8,192 文字を超えるツール出力を「先頭 4,096 文字 + `[... tool result middle pruned ...]` + 末尾 1,024 文字」に切り詰める。**直前に読んだばかりの結果も対象になる**ので、モデルが中身を見る前にコードが消えていた。誤りは閾値を超えた 9 件目付近から出ており、最初の要約より前に起きている。
- 唯一合格した回は、モデル自身が省略に気づき、`offset`/`limit` で読み直して 2 件を訂正していた。
- 履歴の圧縮（要約）自体は正しく働き、圧縮の前後で作業は続いていた。

**修正**

1. 切り詰めの基準をモード設定にした（`toolResultPruneThresholdChars` / `HeadChars` / `TailChars`）。既定は 24,000 / 12,000 / 6,000 文字に引き上げた。DSH の既定値はクラウドの料金を前提にしたもので、131k コンテキストのローカルモデルには厳しすぎる。
2. システムプロンプト（タスク間で固定）に「省略の印を見たら、その範囲を読み直す。見ていない値を推測しない」を追加した。

**回帰確認**: 修正後、公式項目 #1 #2 #4 #5 #8 を STRATA（`unsloth-ud-iq4_xs-v31`）で再実行し、すべて合格した（[bench/2026-11-20T10-27-58-strata-unsloth-regression.md](bench/2026-11-20T10-27-58-strata-unsloth-regression.md)）。

**補足**: 3 回とも、モデルは `task_memory` のメモを使わず、進捗を `codes.txt` に書き出して管理した。そのため「圧縮後のメモ再注入」は実機では発生していない（仕組み自体はモックで確認済み）。
