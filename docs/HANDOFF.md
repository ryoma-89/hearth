## 3. 次にやること（優先順）

### 3.1 Phase 5: 評価用ベンチマーク（**完了**: [phase5-report.md](phase5-report.md)。以下は当初の計画として残す）

依頼文の Phase 5 は「同じタスクで実装を評価し、成功率・処理時間・ツール呼び出し回数・トークン消費量・失敗原因を記録できるようにする」。テスト項目は次の 8 つ。

1. 複数ファイルを読み込んで回答する
2. Python プログラムを生成・実行・修正する
3. LaTeX を生成して PDF 化する
4. 途中でエラーが発生しても適切に復旧する
5. 20 回以上のツール呼び出しを含むタスクを処理する
6. タスク中断後に状態を復元する
7. 複数のタスクをキューに登録する
8. 危険なファイル操作を適切に防止する

実装の方針案:

- `bench/tasks/<name>/` に、初期ファイル（fixture）、プロンプト、**モデルの回答に依存しない合否判定**（生成物の検査スクリプト、期待値）を置く。
- `hearth bench [--suite all] [--repeat N] [--mode ...] [--model ...]` で、タスクごとに一時ワークスペースを作り、デーモン経由で実行し、`TaskRecord.metrics` と判定結果を JSON と Markdown（`docs/bench/<日時>.md`）に出力する。
- 失敗原因の分類: `verification_failed` / `budget_exhausted(kind)` / `MALFORMED_RESPONSE` / ポリシー拒否 / タイムアウト / 合否判定の不合格（タスク自体は succeeded）。
- モックモデル用のシナリオも用意し、ベンチマーク基盤そのものを e2e テストで検証する。実モデルでの結果は「実機」と明記して記録する。
- 6（中断・復元）は「N ステップ後にキャンセル → resume → 合否判定」を自動化する。7 はモックの `peakConcurrency` か、デーモンの推論スロット記録で同時推論数 1 を確認する。

完了条件: モックでの全項目の自動実行と、STRATA で各項目 3 回以上の実行・記録。結果の表を `docs/` に残す。

### 3.2 長時間タスクでの圧縮の実機検証（**一部完了**: 閾値を下げた設定で 3/3 合格。DSH の tool-result-pruner の問題を発見して修正済み。phase5-report.md §5）

- 131k コンテキストで DSH の圧縮（`compaction-basic`、Hearth 側の閾値 0.7〜0.8、headroom 8192）が実際に起きる規模のタスクを STRATA で実行する。確認するのは、`memory-reinjected` テレメトリが出ること、圧縮後も作業が続くこと、`task_memory search_history` が使えること。
- 圧縮の要約リクエストが推論リースを取ること、要約にかかる時間も記録する。

### 3.3 最適化の候補（計測してから判断する）

- **プリフィル量の削減**: system prompt とツール定義で 1 リクエスト約 4〜5k トークン（ツール約 19 個）。モード別にさらにツールを絞る効果を計測する。STRATA のプレフィックスキャッシュは効いている（`cacheReadTokens`）。
- **DSH の起動コスト**: タスク毎に約 2 秒。DSH の `sdk` プロファイル（JSON-RPC）で常駐プロセスにする案があるが、タスク単位の予算プラグインの状態がプロセス全体で共有されているので、ランナーの設計変更が必要になる。
- 推論キューの公平性（現在は FIFO）とタスク優先度。

### 3.4 残っている機能

- `hearth restore <task-id> [path]`: `.hearth/runs/<id>/backup/manifest.jsonl` からの復元。GUI にもボタンを付ける。
- 実行中タスクへの承認 UI: headless には承認チャネルが無いため、現状は危険操作を常に拒否している。DSH の承認の仕組み（`dsh-user-approval`）を GUI につなぐ設計が要る。
- リモートアクセス（Tailscale）・ユーザー管理・利用制限: **外部公開を伴うので、設計案を出して利用者の承認を得てから実装する。**
- 型検査・リンタの組み込み検証器（現状は `--verify` で任意コマンドとして指定できる）。
- GUI: 過去ログを再表示したとき、一部のタスクで生成速度が出ない。トークン単位のストリーミング表示は DSH headless の仕様上できない。

既知の制約の一覧は [known-issues.md](known-issues.md)。

## 4. 落とし穴（実際に踏んだもの）

1. **DSH はプラグインのロード失敗を警告で済ませる。** → 全 Hearth プラグインが `plugin-ready` を出し、ランナーがそれを待つ仕組みにした。新しいプラグインにも必ず入れる。
2. **壊れたツール引数 JSON で DSH のターンが終わる**（`MALFORMED_RESPONSE`）。→ `toolcall-repair` で対処済み。
3. **`compaction-basic` は `headroomTokens: 0` でロードに失敗する。** → オーバーレイで `maxTokens` を明示した。
4. **`session/event` の中からセッションに追記すると衝突する。** → `agent/pre-step` で次ステップに載せる。
5. **ACL サンドボックスは作業フォルダにフルコントロールが必要。** → doctor でチェックし、失敗を検知したら即停止する。
6. **STRATA の `:18500` はエンジン内部用。** 利用者向けは `:47831`。
7. **PowerShell の配列引数**（`'a','b'`）は AST 上 1 要素になる。→ `ps-ast.ps1` で分解している。
8. **DuckDuckGo は自動アクセスをボット検知する。** 回避しない。
9. Python の書き込みで CRLF が混入した。Git Bash の `grep` では検出できない。

## 5. 依頼者の原則（元の依頼から要約）

- 既存実装（特に DSH）を最大限再利用し、無駄に再実装しない。
- 既存の STRATA 環境と設定を壊さない。
- 各機能に単体テストを付ける。ハードコードを避け、設定ファイルから変えられるようにする。エラーを握りつぶさない。
- 実行できなかったテストを成功扱いにしない。LLM が使えない場合はモックで試験し、実モデル未検証と明記する。
- 大規模な破壊的変更や外部公開は、事前に承認を得る。
- 各 Phase の完了時に、実装内容・実行したテスト・結果・未解決の問題を記録する。
